# UniSpot Database Models

*PostgreSQL data design for automated venue allocation and conversational booking*

Product: UniSpot  
Document: Database Models and Integrity Specification  
Version: 1.0  
Date: 28 September 2026

# 1 Purpose and database principles

This document defines the PostgreSQL model for UniSpot's FastAPI backend. The schema supports deterministic venue allocation, venue maintenance blocks, user and organization authorization, conversational booking, notifications, idempotency, and auditability. It removes approval-specific fields and relationships from the ordinary booking path because bookings are allocated automatically.

- PostgreSQL is the authoritative data store.
>
- All identifiers use UUIDs generated by the server or PostgreSQL.
>
- All timestamps are timezone-aware timestamptz values stored in UTC.
>
- Availability is derived from confirmed or held occupied ranges and active venue blocks.
>
- The database prevents overlapping occupied intervals for the same venue.
>
- The assistant uses FastAPI service methods; it has no direct database login or arbitrary SQL capability.
>
- Changes that affect allocation or access produce append-only audit events.

| **Relationship**                     | **Cardinality** | **Delete behavior**                                                                          |
|--------------------------------------|-----------------|----------------------------------------------------------------------------------------------|

| bookings to notifications            | 1 to many       | Set booking_id null only if deletion is permitted; otherwise retain                          |

# 6 Booking integrity constraints

PostgreSQL should reject an overlapping occupied range even if a defect or concurrent request bypasses an earlier application check. The exclusion constraint is the final integrity boundary. The btree_gist extension enables equality comparison on venue_id in the same GiST constraint.

> CREATE EXTENSION IF NOT EXISTS btree_gist;
>
> ALTER TABLE bookings
>
> ADD CONSTRAINT ck_booking_time
>
> CHECK (ends_at \> starts_at);
>
> ALTER TABLE bookings
>
> ADD CONSTRAINT ck_booking_cancellation
>
> CHECK (
>
> (status = 'CANCELLED' AND cancelled_at IS NOT NULL)
>
> OR (status \<\> 'CANCELLED' AND cancelled_at IS NULL)
>
> );
>
> ALTER TABLE bookings
>
> ADD CONSTRAINT ex_booking_venue_time
>
> EXCLUDE USING gist (
>
> venue_id WITH =,
>
> occupied_range WITH &&
>
> )
>
> WHERE (status = 'CONFIRMED');

Venue blocks and bookings occupy different tables, so a single cross-table exclusion constraint cannot compare them. The booking transaction must lock the venue, verify no overlapping active block, and then insert the booking. Alternatively, a unified venue_reservations table may represent both bookings and blocks if the team wants one database-native overlap constraint across all occupancy types.

# 7 Recommended unified occupancy option

For the strongest and simplest database guarantee, introduce venue_reservations as the common occupied-range table. A reservation row represents either a booking, a maintenance block, or another closure. Bookings and venue blocks reference the reservation row one-to-one. The exclusion constraint then protects every occupied interval in one place.

| **Field**        | **Type**         | **Constraint / purpose**                             |
|------------------|------------------|------------------------------------------------------|
| id               | uuid             | Primary key                                          |
| venue_id         | uuid             | Foreign key to venues                                |
| reservation_type | reservation_type | BOOKING or BLOCK                                     |
| occupied_range   | tstzrange        | Required \[start, end) interval                      |
| active           | boolean          | Only active rows participate in exclusion constraint |
| created_at       | timestamptz      | Creation time                                        |

> ALTER TABLE venue_reservations
>
> ADD CONSTRAINT ex_venue_reservation_time
>
> EXCLUDE USING gist (
>
> venue_id WITH =,
>
> occupied_range WITH &&
>
> )
>
> WHERE (active);

Recommendation: use the unified occupancy model unless implementation simplicity for a classroom prototype outweighs the benefit. If separate tables are retained, every booking path, including assistant tools and administrative imports, must use the same transaction and venue-locking service.

# 8 Transaction design

**1.** Begin a database transaction and resolve the authenticated user and active organization membership.

**2.** Load and lock the venue row with SELECT FOR UPDATE so booking and block creation for that venue serialize.

**3.** Validate venue status, capacity, operating hours, booking policy, and requested interval.

**4.** Check for an overlapping active venue block and any occupied booking range.

**5.** Insert the booking immediately as CONFIRMED. The web interface or assistant must collect and validate all required details before this transaction begins.

**6.** Insert the booking event, audit event, and notification outbox record in the same transaction.

**7.** Commit. Map a PostgreSQL exclusion violation to HTTP 409 Conflict and return current alternatives.

# 9 Assistant data access

The assistant requires logical read and write capability, not direct database rights. Its tool adapter calls domain services with the authenticated user context. The service chooses queries and mutations; the model supplies only schema-validated arguments such as date, capacity, venue ID, event name, and confirmation intent.

| **Operation**      | **Repository access**                            | **Authorization boundary**                                     |
|--------------------|--------------------------------------------------|----------------------------------------------------------------|
| Search venues      | SELECT active venue/facility catalogue           | Any authenticated user; public fields only                     |
| Check availability | SELECT occupancy and blocks                      | Return free/busy data without private organizer details        |
| Create booking     | INSERT booking/event/audit/outbox in transaction | Server-injected user; active membership; explicit confirmation |
| List bookings      | SELECT bookings by requester_id                  | requester_id comes from access token, never tool arguments     |
| Cancel booking     | UPDATE owned eligible booking plus events        | Ownership, state, and deadline checks                          |

If separate PostgreSQL roles are used, the API service account may receive only the table privileges needed by repositories. A read-only analytics account should be separate. There should be no database role or credential issued to the language model provider.

# 12 Data validation rules

- ends_at must be later than starts_at; expected_attendance and venue capacity must be positive.
>
- expected_attendance must not exceed venue capacity at booking time.
>
- The requester must have an active membership in the selected organization.
>
- The venue must be ACTIVE and the interval must fall within applicable operating hours.
>
- CANCELLED requires cancelled_at; active and completed bookings must leave it null.
>
- A cancellation requires the current state to be CONFIRMED and must satisfy the cancellation policy.
>
- Conversation state and tool arguments are convenience data; booking rows remain authoritative.
>
- JSONB fields must not store passwords, access tokens, database credentials, or unnecessary personal data.

# 13 Retention and privacy

| **Data**                    | **Recommended treatment**                                                                                      |
|-----------------------------|----------------------------------------------------------------------------------------------------------------|
| Bookings and booking events | Retain for the university's approved operational and audit period; anonymize where possible after that period. |
| Raw conversation messages   | Use the shortest practical retention; allow redaction or deletion under policy.                                |
| Structured assistant state  | Expire with the conversation unless it became part of a confirmed booking.                                     |
| Tool calls                  | Retain redacted operational facts needed to prove authorization and outcome.                                   |
| Audit events                | Append-only with restricted access; define institutional retention and archive process.                        |
| Idempotency responses       | Expire after the retry window and purge safely.                                                                |

# 15 Model verification checklist

- Alembic migration creates every enum, table, foreign key, check, unique constraint, and index.
>
- Two concurrent overlapping booking inserts cannot both commit.
>
- Back-to-back intervals succeed when no buffer applies.
>
- An active venue block prevents allocation through both web and assistant paths.
>
- Duplicate idempotency keys return the original result without creating another booking.
>
- Assistant cannot specify another requester_id or query private bookings.
>
- Cancelling a booking releases its occupied interval and creates booking and audit events.
>
- Deleting or deactivating entities follows the documented retention rules.
>
- All timestamps round-trip correctly between UTC storage and Africa/Nairobi display.
>
- Approval-specific columns and endpoints are absent from the implemented schema and API.
